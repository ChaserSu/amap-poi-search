# 实战踩坑记录（按真实发生顺序）

## 1. 地理编码把"项目"解析成行政区中心点（影响最大的坑）

**现象**：用 geocode 查"泰州悦天地/泰州市海陵区悦天地"，返回
`level=区县`，坐标 `119.923825,32.492480` 其实是"海陵区行政区中心"，
落在老城区（金鹰附近）。真实悦天地在 `119.922427,32.435380`，南北偏差约 6.3km。

**后果**：
- 距离整列错误：悦天地里的店显示 6000+m，6km 外的金鹰店反而显示 443m；
- 以错误中心做"周边 N 公里"抓取，覆盖圆整体偏移，数据作废只能重抓。

**对策（已固化）**：
- 一律用 **POI 关键字搜索**（`/v3/place/text`，脚本 `locate` 命令）定位项目，
  核对返回的名称、地址后取坐标；
- 若返回中出现 `level=区县/市`，说明被降级，坐标不能用；
- 交付前用"项目内店铺距离应为几十米"做最终验证。

## 2. `count` 字段不诚实，不能作为分裂依据

**现象**：同一次查询里，半径 3km 和 50km 都返回 `count=600`。
该字段存在截断/粗粒度返回，不保证是真实总数。

**对策**：完全不信任 count，改用**满页探测**——
- 某页返回不足 25 条 → 已是末页，拉干净了；
- 第 8 页（累计 200）仍返回满 25 条 → 数据被 200 硬上限截断，强制四分该格。

## 3. 单请求参数翻页硬上限 200 条，与 Key 等级无关

高德官方文档原文："目前搜索是不支持返回全量数据的，同请求参数翻页查询最多支持
获取 200 条数据"。个人/企业 Key 都一样，付费也无法突破单请求上限；
Key 等级只影响**每日总量**与 **QPS**。只能靠"拆空间查询 + ID 去重"获取全量。

## 4. `extensions=all` 才返回电话，高德 MCP 拿不到 tel

- POI 搜索/详情默认 `extensions=base`，无 `tel/tag/biz_ext` 等字段；
- 必须传 `extensions=all` 才有：电话、特色菜 tag、人均 cost、评分、营业时间、
  邮编、官网、邮箱、入口坐标、图片列表等；
- 高德官方 MCP（`mcp.amap.com`）的详情工具未暴露 extensions 参数，
  所以 MCP 永远拿不到电话——必须直接调 REST API。

## 5. 整条区划边界发给多边形接口 → HTTP 413

海陵区边界 790 个顶点、约 16KB，拼进 GET URL 报
`413 Request Entity Too Large`。

**对策（边界本地化）**：边界只保存在本地；API 永远只收 2 顶点的小矩形；
POI 拿回后在本地用射线法判定是否在区界内。无 API 消耗、URL 极短。

## 6. QPS 超限 `CUQPS_HAS_EXCEEDED_THE_LIMIT`

高并发翻页（一次并发 10 个请求）必触发。

**对策**：
- 串行请求 + 每次调用间隔 0.3～0.35s；
- 命中限频/网络错误按 2,4,6... 秒指数退避（上限 20s）；
- Key 的实际 QPS 配额见高德控制台「流量分析-配额管理」，可申请提升。

## 7. "同名店"大多不是重复

泰州 50km 内：沙县小吃 ×62、隆江猪脚饭 ×16、兰州牛肉面 ×16……
地址各不同，是真实连锁/加盟店，不能去重。
18676 家店里真正"同店多 ID"的只有十几家（同名+同地址 或 同名+同本地号码）。

另外，多个 POI 共用 `400`/`100` 开头的品牌客服总机（瑞幸、肯德基等）
属于正常现象，清洗时必须排除这些号码。

## 8. Key 平台类型必须匹配

- 只有「Web服务」类型的 Key 能调 restapi.amap.com；
- 用 JS API / Android / iOS 平台的 Key 调 REST 会报
  `USERKEY_PLAT_NOMATCH (10009)`。加签名 sig 解决不了平台不匹配，不要试。
- Key 无效/删除/IP 白名单等问题分别对应 10001/10003/10004 等错误码。

## 9. 周边搜索 radius 上限 50000m

`/v3/place/around` 文档明确：radius 取值 0～50000，超过按默认值处理。
但本技能的 circle 模式用"小矩形网格拼圆"，不走 around 接口，
理论上不受 50km 限制（受每日配额约束）。注意 around 接口才有 `distance_m`，
polygon 接口该字段为空，距离一律以本地 Haversine 结果为准。

## 10. 几何边界与 adcode 双标准交叉验证（增强可信度）

海陵区实测：5360 条保留 POI **100%** 同时满足
"坐标点在边界多边形内"和"`adcode=321202`"，零分歧。
这种双独立标准一致是很好的数据质量信号；若出现分歧，优先相信几何边界并人工抽查。

## 11. CSV 用 utf-8-sig

macOS Excel 打开普通 UTF-8 的 CSV 中文可能乱码；加 BOM（`utf-8-sig`）可解决。

## 12. 不要在管道里用 head 观察长任务进程

`python3 long_task.py | head -20`：head 读满 20 行即退出，
Python 随后收到 SIGPIPE 被静默杀死，且管道返回码还是 head 的 0，极具迷惑性。
正确做法：重定向到日志文件，再用 Read/tail 查看。

## 13. 网格 tile 缓存与"搜索几何"强绑定，禁止跨参数复用（隐蔽的覆盖空洞）

**现象**：做 50km 圆形抓取时，为省事复用了"错误中心（偏差 6.3km）那次"
留下的 tile 目录，结果新算法沿旧标记遍历、把旧矩形的内容当成新矩形的内容，
**静默产生覆盖空洞**：海陵区内 5357 家中有 693 家（13%）在最终圆数据里缺失，
包括距项目仅 631m 的店。脚本退出码 0、无失败、日志一切正常，极难发现。

根因：`<d>_<ix>_<iy>` 这些缓存键只在"同一根矩形（同中心、同半径/同区划）"
下才有几何意义；换中心后索引相同的格子落在完全不同的地理位置。

**对策**：
- 每个搜索任务使用**独立、全新的 workdir**；只有"同参数断点续传"能复用；
- 用更小的已有结果集做覆盖审计：如本例"海陵全区结果集应是 50km 圆结果集的
  子集"，差集必须为 0；
- 这条也是"外部数据结构看似命中就跳过查询"类策略的通用教训：缓存键必须
  完整包含所有影响结果的参数（中心、半径、types、adcode）。

## 14. 覆盖性的边界要说清楚

四叉树保证的是"**高德已收录 POI 数据集内**无遗漏"
（外接包围盒 + 不交四分 + 最近点剪枝 + 满页探测，几何上可证）。
高德自身未收录的店（新开张、未标注）任何 API 方案都拿不到，
不要向用户承诺"现实世界里一家不缺"。

## 15. 可用高德兼容中转 mapapi.cc 替代官方域名

`https://mapapi.cc` 的路径、参数、返回 JSON 与 `restapi.amap.com` 完全一致，
实测 `/v3/place/text`（含 tel）与 `/v3/config/district`（含 polyline 边界）均正常，
可用来节省高德官方配额/费用。但要注意：**Key 与域名绑定，不可混用**——
中转 Key 只能打中轉域名，高德 Key 打中转域名会鉴权失败；
脚本通过 `AMAP_BASE` 环境变量切换域名，默认 mapapi.cc。
